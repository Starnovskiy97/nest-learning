# Урок 3. Повтор запроса без повторного создания задачи

## Зачем это нужно

Сервер создал задачу, но клиент не получил ответ из-за сбоя сети. Повтор обычного
POST может создать вторую задачу. Nginx не решает эту проблему: оба запроса могут
укладываться в лимит. Отключение кнопки тоже не защищает от сетевого повтора.
Одинаковые названия задач допустимы — это не признак дубля.

`Idempotency-Key` обозначает одно намерение создать задачу. Это соглашение нашего
API, а не обязательный заголовок для любого POST.

## Контракт POST /tasks

- Заголовок необязателен. Без него каждый корректный POST создаёт новую задачу.
- Если передан, должен содержать один UUID v4. Неверный или пустой ключ даёт 400,
  а не отключает защиту. Регистр UUID не имеет значения.
- Область ключа — конкретный автор и операция создания задачи. Другой автор может
  независимо использовать тот же ключ. Ключ не заменяет JWT.
- Первый успешный запрос возвращает 201 и сохраняет результат.
- Повтор с тем же ключом и `title` возвращает то же тело и статус 201 без новой
  задачи. Сравнивается точная строка после проверки DTO: пробелы и регистр названия
  значимы. Порядок полей JSON значения не имеет.
- Тот же ключ с другим `title` даёт 409 Conflict.
- Новый ключ означает новое действие, даже при одинаковом названии.
- Невалидный DTO и ошибки аутентификации не сохраняются как результат.
- Запоминаются только успешно зафиксированные создания. При откате транзакции
  не остаётся ни задачи, ни записи ключа. После сетевой ошибки повторять нужно
  с тем же ключом: клиент не знает, успел ли сервер зафиксировать результат.

## Проверка через HTTPie

Войти по примерам из [auth.md](auth.md). Для порта 8080 сначала запустить Nginx:
`pnpm proxy:up`. Для прямого API можно заменить порт на 3000.

```bash
KEY=$(node -e "console.log(require('node:crypto').randomUUID())")

http POST :8080/tasks \
  "Authorization:Bearer <JWT>" \
  "Idempotency-Key:$KEY" \
  title="Купить молоко"
```

Повтори команду `http` без генерации нового KEY: ID и тело ответа останутся
теми же. Затем поменяй только `title` — получишь 409. Чтобы намеренно создать
ещё одну задачу, сгенерируй новый KEY.

На фронтенде `crypto.randomUUID()` вызывается **один раз на действие**, не внутри
каждой повторной попытки fetch. Для новой попытки доставки сохраняются ключ
и исходное тело. Если повторы должны переживать перезагрузку страницы, эти данные
нужно сохранять на клиенте. Наша реализация сама этого не делает.

## Где хранится результат

В PostgreSQL добавлена таблица `TaskCreationRequest`:

```text
ownerId + key → title + taskId
```

Составной первичный ключ `(ownerId, key)` не позволяет зафиксировать два результата
одного действия пользователя. UUID хранится как PostgreSQL UUID.

`title` и `taskId` вместе с `ownerId` — минимальный снимок ответа нашего POST.
При создании `completed` всегда false, а `assigneeId` всегда null. Ответ
также содержит начальную `version: 1`, не текущую версию задачи. Подробнее:
[task-concurrency.md](task-concurrency.md).
Весь снимок восстанавливается без JSON-колонки. Если контракт создания изменится, нужно
пересмотреть формат снимка и совместимость с уже сохранёнными результатами.

`taskId` намеренно не является внешним ключом на Task: результат сохраняется
после удаления задачи. После изменения задачи повтор возвращает первоначальный
ответ, а не текущее состояние. После удаления повтор также возвращает исходный
201, но **не воскрешает задачу**: GET по её ID вернёт 404. Актуальное состояние
получают через GET.

## Почему простой проверки ключа недостаточно

```text
Запрос A: ключа нет
Запрос B: ключа тоже нет
Запрос A: создаёт задачу
Запрос B: тоже создаёт задачу
```

Предварительная проверка не блокирует второй запрос. Основная гарантия —
уникальность в базе и транзакция, а не `findUnique` перед записью.

В `TasksService.create()`:

1. Проверить формат ключа; поискать сохранённый результат для автора.
2. Если результата нет, в транзакции создать задачу и записать её снимок.
3. Зафиксировать обе записи вместе.
4. Если другой запрос опередил нас, вставка ключа получает Prisma `P2002`.
   Транзакция проигравшего откатывается вместе с его задачей.
5. Уже **вне** неуспешной транзакции прочитать результат победителя и вернуть его
   либо 409 при другом теле. Неожиданные ошибки не скрываются под успешный повтор.

Конкурент может ждать завершения записи того же ключа. Действуют таймауты
транзакции/соединения: если запрос завершился ошибкой, повторять нужно со старым
ключом. ID задач могут иметь пропуски: откат не возвращает использованное значение
sequence — это нормально.

Гарантия работает между экземплярами приложения с одной базой. Map, Redis
и блокировка кнопки не участвуют в этой реализации.

## Проверки

```bash
pnpm test:e2e --runInBand task-idempotency
```

Тесты в отдельной случайной схеме проверяют обычное создание, повтор после
перезапуска, конфликт тела, независимость пользователей и ключей, снимок после
изменения/удаления, проверку заголовка и аутентификации, параллельные запросы
через два приложения с общим тестовым Prisma Client. Отдельный тест принудительно
даёт двум предварительным чтениям ответ «ключа нет», после чего реальные
транзакции и уникальное ограничение доказывают откат дубля.

## Ограничения учебного этапа

- Только POST /tasks, не глобальный механизм для всех маршрутов.
- Ключи без TTL и автоматической очистки: таблица будет расти. В продакшене срок
  хранения и поведение после истечения задают явным контрактом.
- Не защищает от клиента, создающего новый ключ на каждый запрос:
  для ограничения нагрузки нужны отдельные лимиты и квоты.
- Снимок сохраняет исходный title после удаления задачи; политику удаления таких
  данных нужно учитывать отдельно. Записи также ссылаются на пользователя.
- Транзакция включает только PostgreSQL. Письма, платежи и вызовы других сервисов
  автоматически не откатываются; для них нужны отдельные механизмы согласования,
  например outbox и идемпотентный получатель.
- Это не универсальное обещание «exactly once»: гарантируется не более одной
  зафиксированной задачи на сохранённый ключ автора при использовании этого API.

Миграция добавляет только новую таблицу; существующие пользователи и задачи
не меняются. Очистка тестов дополнена таблицей только внутри тестовой схемы.

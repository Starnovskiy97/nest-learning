# Урок 8. Инвалидация кэша без воскрешения старых страниц

## Почему не просто DEL

У автора есть страницы с разными фильтрами и пагинацией. После изменения задачи
нужно перестать использовать все потенциально затронутые варианты. Удаление ключей
по шаблону сложно и не защищает от следующей гонки:

```text
A: прочитал старые задачи из PostgreSQL, ещё не записал кэш
B: изменил задачу и удалил старый кэш
A: записал старые задачи обратно
C: прочитал устаревший кэш
```

## Поколение в ключе

```text
До изменения:    tasks:user7:g12:фильтры:страница
После изменения: tasks:user7:g13:фильтры:страница
```

GET фиксирует текущее поколение **один раз до чтения кэша/задач**. При miss он
записывает результат именно под этим поколением, не перечитывает его перед SET.

```text
A: прочитал поколение 12 и старые задачи
B: изменил задачу и зафиксировал поколение 13
A: поздно записал старый снимок под g12
C: прочитал поколение 13 → g12 никогда не выбирается
```

Если бы A взял новое поколение перед SET, он мог бы записать старые данные под
новым ключом и сломать защиту. TTL 5 секунд убирает старые страницы физически;
для логической инвалидации ждать его не нужно. Сканировать и удалять все ключи
автора не требуется. Чужие пользователи не затрагиваются.

## Почему счётчик в PostgreSQL, а не в Redis

Схема «COMMIT PostgreSQL → INCR Redis» имеет окно сбоя: приложение может упасть
между операциями или Redis окажется недоступен. Задача изменится, а старый кэш
останется выбранным. Дополнительные retries сами по себе не делают операции атомарными.

Здесь используется другой компромисс: `User.taskCacheGeneration` хранится
в PostgreSQL, и изменение задачи с увеличением поколения выполняются **в одной
транзакции**. Если увеличение не удалось, откатывается и изменение задачи.
Redis хранит только страницы, никакого INCR в нём нет.

```text
BEGIN
  INSERT / UPDATE / DELETE Task
  UPDATE User SET taskCacheGeneration = taskCacheGeneration + 1
COMMIT
```

Это работает и при отключённом Redis. После его восстановления старые страницы
не станут актуальными: счётчик в PostgreSQL уже увеличен. Поколение не исчезнет
из-за вытеснения ключа Redis или перезапуска Redis. Не нужна общая транзакция
между PostgreSQL и Redis, потому что атомарно изменяемые данные находятся в одной БД.

## Когда увеличивается поколение

- Успешный POST без ключа: один раз.
- Успешное создание с Idempotency-Key: один раз вместе с задачей и снимком.
- Повтор уже выполненного создания: не увеличивается.
- Успешный PATCH, включая version-only: один раз вместе с версией задачи.
- Успешный DELETE: один раз.
- Невалидный запрос, чужая/отсутствующая задача, конфликт версии или откат:
  поколение не меняется.

При конкурентных записях используется атомарный increment, не «прочитать число
и сохранить число + 1». Это предотвращает потерю увеличений.

## Цена и границы гарантии

На GET с готовым Redis добавлен SELECT одного поля пользователя перед GET кэша.
Даже hit теперь требует этого запроса плюс проверки пользователя в Guard.
Экономим более дорогую транзакцию списка и count, но не все обращения к БД.
Если Redis выключен или не готов, SELECT поколения пропускается и используется
обычный SQL-путь. Ошибка PostgreSQL при чтении поколения не заменяется старым кэшем.

Каждая запись задачи также обновляет строку автора. При множестве параллельных
записей одного пользователя эта строка становится точкой конкуренции. Транзакции
добавляют работу и ожидание соединений: это не бесплатная оптимизация и не
универсальный вариант для всех высоконагруженных систем.

Гарантия относится к новым запросам, которые читают основную PostgreSQL после
commit изменения через этот API. Уже начавшееся чтение может вернуть старый
ответ после завершения записи — отмены HTTP-запросов и упорядочивания ответов нет.
Клиенту всё ещё нужна защита от поздних ответов и проверка версии на PATCH.
Чтение поколения с отстающей read replica изменило бы гарантию; здесь реплик нет.

Прямой SQL, Studio, фоновые обработчики и старые версии API должны тоже менять
поколение в одной транзакции с задачей. Писатели, обходящие это правило, защищены
лишь TTL, не немедленной инвалидацией. Передача владения потребовала бы смены
поколений старого и нового владельцев; публичный API сейчас её не предоставляет.

При восстановлении старого снимка БД, сбросе/повторном использовании ID пользователей
или изменении контракта кэша нужно сменить namespace Redis. Не смешивать разные
окружения под одним namespace. Не сбрасывать поколение ради «очистки» кэша.

Поколение — PostgreSQL BIGINT и JavaScript bigint, чтобы не упереться в 32-битный
счётчик. В ключ оно превращается в строку. Поле внутреннее: публичные select
пользователей его не включают, и в JSON API bigint не попадает.
Версия задачи `Task.version` — отдельный механизм, её контракт не менялся.

## Проверка

```bash
pnpm cache:up
pnpm test:cache
```

Кроме базового кэша проверяются:

- Новый список сразу после POST, PATCH и DELETE без ожидания TTL.
- Смена всех вариантов страниц/фильтров и независимость другого пользователя.
- Запись через один экземпляр и чтение через другой.
- Детерминированная гонка: старое чтение приостановлено перед SET, запись уже
  завершилась, затем старый SET разрешён; следующий GET видит новые данные.
- Запись при недоступном Redis и игнорирование старого кэша работающим экземпляром.
- Одно увеличение при конкурентном идемпотентном POST, отсутствие увеличения на replay.
- Отсутствие потерянных увеличений при независимых конкурентных записях.
- Откат задач, версий и записей идемпотентности при искусственной ошибке обновления
  поколения. Ограничение для воспроизведения ошибки создаётся только в тестовой схеме.

Миграция `add_task_cache_generation` добавляет поле с DEFAULT 1 существующим
пользователям, не удаляя данные. Старые Redis-ключи без `g...` не читаются
новым кодом и истекают самостоятельно. Схема публичного ответа API не меняется.

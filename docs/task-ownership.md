# Авторизация задач: доступ только автору

## Правила

- Любой маршрут `/tasks` требует действующий JWT в заголовке Authorization.
- `ownerId` — автор задачи; сервер берёт его из пользователя, установленного Guard.
- `assigneeId` — исполнитель; назначение не предоставляет доступ к задаче.
- Список и `total` включают только задачи текущего автора.
- Читать, изменять и удалять можно только свои задачи.
- Чужая и несуществующая задача возвращают одинаковый 404, чтобы не раскрывать
  факт существования чужого ресурса.
- Без токена — 401. Передача `ownerId` в DTO или query отклоняется с 400.
- Сменить автора через публичный API нельзя.

Владелец может назначить исполнителем другого существующего пользователя.
Это не меняет автора задачи и не расширяет права исполнителя.

## Проверка через HTTPie

Сначала зарегистрироваться и войти по примерам из [auth.md](auth.md).
Подставить полученный `access_token`:

```bash
http POST :3000/tasks \
  "Authorization:Bearer <JWT>" \
  title="Моя задача"

http GET :3000/tasks "Authorization:Bearer <JWT>" page==1 limit==10
http GET :3000/tasks/1 "Authorization:Bearer <JWT>"
http PATCH :3000/tasks/1 "Authorization:Bearer <JWT>" completed:=true
http DELETE :3000/tasks/1 "Authorization:Bearer <JWT>"
```

Использовать фактический ID из ответа создания, не обязательно 1.
Токен другого пользователя не даст прочитать, изменить или удалить эту задачу.

## Архитектура

```text
JwtAuthGuard → request.user
                   ↓
TasksController → TasksService → Prisma where: { id, ownerId }
```

Guard отвечает за аутентификацию: кто отправил запрос.
Сервис отвечает за авторизацию: можно ли этому пользователю работать с задачей.

`TasksModule` импортирует `AuthModule`, который экспортирует Guard и `JwtModule`.
`UsersService` не зависит от задач, поэтому циклической зависимости нет.

Ограничение по автору применяется прямо в запросах базы. В обновлении и удалении
`ownerId` входит в `where` самой операции, а не только в предварительную проверку.
Поля обновления перечислены явно: тело запроса не может заменить `ownerId`.
Пагинация и подсчёт используют одинаковый фильтр с текущим автором.

## Переход для существующих задач

Миграция `add_task_owner` добавляет nullable-поле `ownerId`, внешний ключ
и индекс `(ownerId, id)`. Данные не удаляются, авторы старых задач не угадываются.

Старые задачи имеют `ownerId = NULL` и не видны ни одному пользователю через API.
Их `assigneeId` не используется для автоматического определения автора.
Посмотреть их можно через `pnpm db:studio` и, когда настоящий автор установлен,
явно назначить его ID в `ownerId`. Делать это следует только после проверки
каждой задачи. В этой миграции назначения старым задачам не выполнялись.

Все новые задачи API создаёт с автором. Колонка пока nullable исключительно
для безопасного перехода; после назначения авторов всем старым задачам
можно отдельной миграцией сделать её обязательной.

## Тесты

```bash
pnpm test:e2e --runInBand task-ownership.e2e-spec.ts
```

Проверяются 401 на всех операциях без токена, изоляция списка и счётчика,
запрет доступа исполнителю к чужой задаче, сохранение данных после отказа,
запрет подмены автора и скрытие старых задач без владельца.

# Урок 1. Как понять, нужен ли запросу индекс

## Запуск

```bash
pnpm db:up
pnpm db:lab:indexes
```

Скрипт `scripts/indexes-lab.ts` подключается к локальному PostgreSQL из
`DATABASE_URL`. Создаёт случайную схему `indexes_lab_<uuid>`, применяет в ней
миграции проекта, добавляет 101 пользователя и 300 000 задач. У автора 1
100 000 задач, из них 1000 незавершённых. Распределение намеренно учебное:
оно помогает увидеть разницу между поиском автора и поиском автора со статусом.

Всё выполняется в одной транзакции, которая в конце откатывается, в том числе
при ошибке. Таблицы, индексы и данные приложения не изменяются. При разрыве
соединения незавершённую транзакцию откатывает PostgreSQL. Удаление индекса
в скрипте относится только к новой учебной схеме.

**Изоляция схемы не изолирует ресурсы:** эксперимент использует CPU, память,
диск и WAL того же локального сервера. Не запускать на рабочей базе или во
время важных измерений другого приложения. Проверка адреса разрешает только
локальный хост, но не распознаёт туннель к удалённому серверу: проверь окружение.
Временной лимит каждого SQL-запроса — 60 секунд.

## Какой запрос изучаем

Наш `TasksService.findAll()` выполняет два запроса: страницу и точный подсчёт.
Ниже SQL с той же логикой для одного из вариантов фильтра, не буквальный
текст SQL, сгенерированного Prisma:

```sql
SELECT * FROM "Task"
WHERE "ownerId" = 1 AND completed = false
ORDER BY id LIMIT 10;

SELECT count(*) FROM "Task"
WHERE "ownerId" = 1 AND completed = false;
```

`LIMIT 10` относится к странице, но не ограничивает работу второго запроса.
Подсчёт должен учесть все подходящие строки.

## Что такое индекс

Индекс — отдельная структура данных со значениями колонок и ссылками на строки.
Используемые здесь индексы PostgreSQL по умолчанию — B-tree: упорядоченное
дерево, позволяющее находить нужный диапазон без просмотра всей таблицы.

Для `(ownerId, id)` записи упорядочены сначала по автору, внутри автора — по ID:

```text
ownerId=1 → id=1, 2, 3, ...
ownerId=2 → id=100100, 100200, ...
```

Это подходит для `WHERE ownerId = ... ORDER BY id LIMIT ...`.
Но `completed` в таком индексе нет: проверка статуса требует дополнительной работы.

Индекс `(ownerId, completed, id)` группирует записи ещё и по статусу.
При равенстве автора и статуса нужные ID уже идут по порядку.
Он не обязательно заменяет `(ownerId, id)`: без фильтра статуса порядок
всех задач автора по ID из него напрямую не получается.

Цена каждого индекса — место, затраты на создание и обслуживание при записи.
В частности, изменение `completed` затрагивает индекс, содержащий эту колонку.
Поэтому не добавляем индексы на все комбинации фильтров.

## Как читать EXPLAIN

Скрипт выводит `EXPLAIN (ANALYZE, BUFFERS)` для каждого сценария.
`ANALYZE` здесь **действительно выполняет запрос**. Не запускать его бездумно
на изменяющих данные запросах или тяжёлых запросах рабочей базы.
Отдельная команда `ANALYZE "Task"` перед измерениями обновляет статистику
для планировщика — это другое применение слова ANALYZE.

- `Seq Scan` — последовательный просмотр таблицы; не обязательно проблема.
- `Index Scan` — чтение через индекс с обращением к строкам таблицы.
- `Bitmap Index Scan` + `Bitmap Heap Scan` — сначала найти адреса строк,
  затем читать нужные страницы таблицы.
- `Index Cond` — условие, применяемое при поиске в индексе.
- `Filter` — дополнительная проверка после чтения кандидатов.
- `Rows Removed by Filter` — сколько кандидатов отброшено проверкой.
- `rows` до `actual` — оценка; внутри `actual` — фактическое число строк.
- `loops` — число выполнений узла; фактические строки и время указаны в среднем
  за выполнение. Учитывай это, в частности, в параллельных планах.
- `cost` — условная оценка планировщика, **не миллисекунды**.
- `Execution Time` — время выполнения в миллисекундах, не время HTTP-запроса.
- `Buffers: shared hit` — обращения к блокам в буферах PostgreSQL;
  `read` — загрузки блоков в них, возможно из кэша ОС, не обязательно с диска.
  Значения родительских узлов включают работу дочерних: не суммируй их все.

## Что получилось в первом запуске

Один локальный запуск на 300 000 задачах; значения ниже — пример, не норматив:

| Сценарий | Execution Time | Наблюдение |
| --- | ---: | --- |
| Подсчёт по автору и статусу без индекса автора | 9,15 мс | Parallel Seq Scan |
| Тот же подсчёт с `(ownerId, id)` | 6,07 мс | Найдено 100 000 кандидатов, 99 000 отброшено |
| Тот же подсчёт с дополнительным `(ownerId, completed, id)` | 0,24 мс | В индексе найдены нужные 1000 кандидатов |
| Страница с `OFFSET 90000` | 7,09 мс | Индексный узел выдал 90 010 строк |
| Страница после известного `id = 90000` | 0,017 мс | Индексный узел выдал 10 строк |

Первая страница была быстрой даже без индекса автора: планировщик использовал
первичный ключ, а задачи нужного автора в этом наборе стоят в начале.
Это не доказывает, что индекс автора бесполезен для других авторов и распределений.
В курсорном примере PostgreSQL тоже выбрал первичный ключ: не заставляем его
выбирать заранее желаемый план.

При подсчёте почти всей таблицы (`completed = true`, 99% строк) PostgreSQL
выбрал Parallel Seq Scan. Это разумный вариант, а не повод отключать Seq Scan.

## Почему это ещё не нагрузочный тест

- Запросы выполняются последовательно, нет конкуренции клиентов.
- Данные синтетические; объёмы и распределение влияют на выбор плана.
- Данные и индексы только что созданы, кэши прогреваются по ходу опыта.
- Всё находится в незавершённой транзакции; это отличается от обычной базы
  после COMMIT и VACUUM, в том числе возможностями Index Only Scan.
- Не измеряются HTTP, Guard, Prisma, сеть, запись и задержки `p95/p99`.

Повторные запуски помогают увидеть разброс, но не устраняют все эти ограничения.
Сравнивай прежде всего объём работы и условия индекса, а не только доли миллисекунды.
В рабочую схему дополнительный индекс пока **не добавлен**.

## Пагинация: важное ограничение

Индекс не делает глубокий OFFSET бесплатным: нужно прочитать и пропустить строки.
Условие `id > lastSeenId` позволяет продолжить с известной позиции — это
курсорная (keyset) пагинация. Нельзя получить курсор для произвольной страницы
простым вычислением номера: клиенту нужна позиция, например из предыдущего ответа.
В примере ID 90000 выбран из известного учебного набора.
API пока сохраняет прежнюю пагинацию `page/limit`.

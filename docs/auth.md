# Регистрация, вход и JWT

## Проверка через HTTPie

Использовать только учебный пароль, не свой настоящий:

```bash
http POST :3000/auth/register \
  name="Анна" \
  email="anna@example.com" \
  password="learning-password-123"
```

Ответ — 201 Created:

```json
{
  "id": 1,
  "name": "Анна",
  "email": "anna@example.com"
}
```

Повторная регистрация email возвращает 409 Conflict. Email обрезается
по краям и приводится к нижнему регистру: это выбранное правило приложения.
Неверные данные и неизвестные поля возвращают 400.

## Входные данные регистрации

- `name` — непустая строка с непробельным символом, максимум 100 символов.
- `email` — валидный email, максимум 254 символа после нормализации.
- `password` — строка от 12 до 128 символов, не только пробелы.

Пароль не обрезается и не приводится к нижнему регистру.
`passwordHash` и `id` нельзя передавать в запросе регистрации.

## Архитектура

```text
AuthController → AuthService → PasswordHasherService
                      ↓
                 UsersService → PrismaService → PostgreSQL
```

`AuthModule` импортирует `UsersModule`, а не обращается к таблице напрямую.
`AuthService` управляет регистрацией, `UsersService` сохраняет пользователя,
`PasswordHasherService` отвечает за хеширование.

## Как хранится пароль

Вместо пароля сохраняется строка формата:

```text
scrypt$N$r$p$salt$derivedKey
```

Используется асинхронный `scrypt` из `node:crypto` с параметрами
`N=131072`, `r=8`, `p=1`, случайной солью 16 байт и ключом 64 байта.
Параметры и соль не являются секретом и хранятся вместе с хешем.
Scrypt намеренно требует времени и памяти, усложняя перебор паролей.
Асинхронный вызов выполняет вычисление в пуле потоков Node.js.

Хеширование не является обратимым шифрованием: расшифровать хеш нельзя.
При входе сервер вычисляет хеш введённого пароля с сохранёнными параметрами
и солью, затем сравнивает результаты через `timingSafeEqual`.
Для неизвестного email или отсутствующего хеша тоже выполняется scrypt
с фиктивными значениями: это уменьшает различие времени обработки.

Одинаковые пароли имеют разные хеши благодаря случайной соли.
Тест проверяет и различие хешей, и повторное вычисление с сохранённой солью.

## Защита ответов и уникальность

В `UsersService` публичные запросы используют явный `select`: `id`, `name`, `email`.
Это исключает хеш из регистрации, списка пользователей и поиска по ID.
Одна только аннотация возвращаемого типа TypeScript не удаляла бы поля
из объекта во время исполнения.

Отдельный внутренний метод `findCredentialsByEmail()` возвращает только
`id` и `passwordHash` для входа. Контроллеры пользователей его не вызывают.

Уникальный индекс PostgreSQL защищает email от повторов, в том числе при
одновременных запросах. Ошибка Prisma `P2002` преобразуется в HTTP 409.

## Существующие пользователи

Миграция добавляет nullable-колонки `email` и `passwordHash`, не удаляя
существующие записи. Старые пользователи сохраняют `null` в этих колонках.
`POST /users` пока остаётся учебным способом создать пользователя без
учётных данных. Его ответ теперь также включает `email: null`.

Ни регистрация, ни создание пользователя сейчас не выдают токен.

## Вход

```bash
http POST :3000/auth/login \
  email="anna@example.com" \
  password="learning-password-123"
```

Ответ — 200 OK:

```json
{
  "access_token": "<JWT>",
  "token_type": "Bearer",
  "expires_in": 900
}
```

Email нормализуется так же, как при регистрации; пароль не изменяется.
Для входа допускается пароль от 1 до 128 символов: правила создания пароля
проверяются при регистрации, а не повторно при каждом входе.
Неверный пароль, неизвестный email и пользователь без хеша получают одинаковый
401 с сообщением `Invalid email or password`. Неверная форма запроса даёт 400.

JWT выдаёт `JwtService` из `@nestjs/jwt`. Он содержит `sub` — ID пользователя,
`iat` — время выдачи, `exp` — время окончания действия, а также `iss` и `aud`.
Пароль, хеш и email в токен не записываются. JWT подписан, но не зашифрован:
его содержимое может прочитать любой, у кого есть токен.

## Секрет подписи

`JWT_SECRET` хранится в `.env`, а не в коде. Приложение откажется запускаться,
если секрет отсутствует или короче 32 байт. Для нового окружения:

```bash
node -e "console.log(require('node:crypto').randomBytes(48).toString('hex'))"
```

Результат нужно записать в `.env` как `JWT_SECRET=...`. Локальный секрет уже
сгенерирован. `.env.example` содержит только пустое поле, не рабочий секрет.
Не передавать секрет подписи клиенту и не сохранять его в Git.

Срок токена — 15 минут. Изменение секрета делает ранее выданные токены
недействительными. E2E-тесты используют отдельный заведомо тестовый секрет.

## Защищённый маршрут

Скопировать `access_token` из ответа входа:

```bash
http GET :3000/auth/me "Authorization:Bearer <JWT>"
```

Без заголовка или с неверным токеном — 401. При успехе ответ содержит текущего
пользователя: `id`, `name`, `email`, без хеша.

```text
Authorization: Bearer <JWT>
        ↓
JwtAuthGuard: подпись HS256, срок, issuer, audience, sub
        ↓
UsersService: пользователь ещё существует?
        ↓
request.user = безопасные поля пользователя
        ↓
AuthController.getMe()
```

`@UseGuards(JwtAuthGuard)` прикреплён только к `GET /auth/me`.
Guard не просто декодирует JWT, а проверяет его через `verifyAsync()`.
Просроченный токен, неверная подпись, другой алгоритм, issuer или audience,
отсутствующий срок и удалённый пользователь отклоняются.
Неожиданные ошибки базы не маскируются под неверный токен.

Токен принимается только из заголовка Authorization, не из query-параметра.
Ответы входа и `/auth/me` имеют `Cache-Control: no-store`.

Изменений схемы базы для этого этапа не требуется.

## Что ещё не реализовано

- Защита маршрутов пользователей и задач: `/users` и `/tasks` пока открыты.
- Проверка владения задачами и роли.
- Refresh-токены, выход с отзывом токена и отзыв токенов при смене пароля.
- Подтверждение email, восстановление пароля и ограничение частоты запросов.

Это локальный учебный этап, не готовая система для публичного размещения.
Хеширование потребляет заметные ресурсы; перед публичным запуском нужны
ограничения частоты и параллельности запросов, а также HTTPS.

# Урок 7. Redis-кэш списка задач

Продолжение реализовано: [инвалидация по поколению](cache-invalidation.md).
Теперь TTL очищает старые записи, а после API-записи новые запросы выбирают новое поколение.

## Что кэшируем

Только GET /tasks: `{ items, total, page, limit, totalPages }`.
Используется cache-aside:

```text
JWT Guard → пользователь существует? → проверка DTO
                                          ↓
                          прочитать поколение из PostgreSQL
                                          ↓
                                    Redis GET
                      есть запись ↙              ↘ нет / ошибка
                 проверить формат             PostgreSQL
                    вернуть                   Redis SET EX 5
                                                  вернуть
```

JWT и загрузка пользователя выполняются каждый раз. На hit пропускается
транзакция выборки и подсчёта задач, но остаются запрос пользователя в Guard
и короткое чтение поколения. При отключённом/не готовом Redis чтение поколения пропускается.
GET одной задачи, POST, PATCH и DELETE по-прежнему работают с PostgreSQL.
Кэш не является источником истины и не участвует в идемпотентности или проверке
версии PATCH. Ответ списка имеет Cache-Control: no-store: Redis здесь внутренний
кэш сервера, а не разрешение браузеру/прокси сохранять персональные ответы.

## Запуск

```bash
pnpm db:up
pnpm cache:up
pnpm start:dev
```

Redis уже поднят при реализации этого этапа. Его адрес на компьютере:
`redis://127.0.0.1:6380`. Это также адрес по умолчанию, если REDIS_URL отсутствует
в `.env`. Пример параметров добавлен в `.env.example`:

```dotenv
REDIS_URL=redis://127.0.0.1:6380
TASK_CACHE_NAMESPACE=nest-learning:tasks:v1
```

При изменении окружения перезапусти приложение. Пустая REDIS_URL отключает клиент:

```bash
REDIS_URL= pnpm start:dev
```

`pnpm cache:stop` останавливает только Redis. Приложение продолжает читать базу
и восстанавливает соединение с Redis в фоне. `pnpm db:down` по-прежнему останавливает
Compose-проект; не применять `down -v`, если нужны данные PostgreSQL.
Путь через Nginx на 8080 также работает после `pnpm proxy:up`.

## Ключи и TTL

```text
nest-learning:tasks:v1:7:g12:false:any:1:10
namespace : ownerId : generation : completed : assigneeId : page : limit
```

Ключ строится из пользователя Guard, поколения из PostgreSQL и значений FilterTasksDto:
completed, assigneeId, page, limit. Отсутствующий фильтр отличается от false;
отсутствие page/limit совпадает с явными значениями по умолчанию. Клиент не может
выбрать чужой ownerId в query.

Разным базам/окружениям на одном Redis нужны разные namespace. Экземплярам
одного приложения с одной базой — одинаковый namespace. При изменении формата
ответа можно сменить версию namespace, чтобы не читать старый формат.

`SET ... EX 5` задаёт TTL 5 секунд от записи в Redis. GET срок не продлевает.
Пустые списки тоже кэшируются. Инвалидация теперь выполняется сменой поколения,
а TTL нужен для удаления уже не используемых страниц.

## Ручная проверка

Используй JWT зарегистрированного пользователя:

```bash
http GET :3000/tasks "Authorization:Bearer <JWT>"
http GET :3000/tasks "Authorization:Bearer <JWT>" page==1 limit==10

docker compose --profile cache exec redis redis-cli --scan \
  --pattern 'nest-learning:tasks:v1:*'
```

Эти два HTTP-запроса используют один ключ, если между ними не было записи.
Ниже пример для пользователя 7 и поколения 12; подставь реальный ключ из --scan:

```bash
docker compose --profile cache exec redis redis-cli TTL \
  'nest-learning:tasks:v1:7:g12:any:any:1:10'

docker compose --profile cache exec redis redis-cli GET \
  'nest-learning:tasks:v1:7:g12:any:any:1:10'
```

TTL уменьшается; -2 означает, что записи уже нет. Если проверяешь слишком поздно,
повтори HTTP-запрос и проверь снова. Не использовать FLUSHALL/FLUSHDB: они удаляют
не только ключи текущего приложения или теста.

Само наличие записи не доказывает hit. В `pnpm test:cache` проверено напрямую,
что повторный GET не вызывает Prisma.$transaction.

## Свежесть после записи

Первый этап полагался только на TTL и намеренно возвращал старый список после записи.
Теперь POST/PATCH/DELETE увеличивают User.taskCacheGeneration в той же транзакции,
что и изменение задачи. Новый GET после commit выбирает новый ключ и не использует
предыдущее поколение. Поздний SET старого чтения также остаётся в старом поколении.

Уже выполняющийся GET всё ещё может вернуть старый результат: инвалидация не отменяет
запросы в полёте и не упорядочивает ответы браузера. Прямые SQL-записи и другие
писатели обязаны обновлять поколение сами; новые права доступа требуют отдельного
пересмотра инвалидации. Подробности и гонка — в [cache-invalidation.md](cache-invalidation.md).

## Отказы и ограничения

- Подключение фоновое, запуск приложения не ждёт Redis. Пока клиент не ready,
  запросы идут в PostgreSQL; offline-очередь отключена.
- Таймаут GET/SET Redis — 100 мс, подключения — 300 мс. Это не общий дедлайн HTTP.
  На miss могут последовательно ожидаться GET и SET.
- Ошибка GET Redis означает miss. Ошибка SET не отменяет успешное чтение БД.
  Ошибки PostgreSQL не превращаются в пустой список.
- Неверный JSON, чужой ownerId, неподходящие поля/фильтры означают miss.
  Из кэша возвращаются только публичные поля, дополнительные поля отбрасываются.
- В логи не выводятся URL Redis, токены и содержимое задач. Предупреждение
  о недоступности выводится один раз до восстановления соединения.
- Redis настроен с maxmemory 64mb и allkeys-lru: запись может вытесниться раньше
  TTL. RDB/AOF выключены, постоянного тома нет: потеря кэша допустима.
  maxmemory не ограничивает всю память процесса/контейнера жёстким пределом.
- Порт опубликован только на loopback, без пароля/TLS — для локального обучения.
  В продакшене нужны сетевая изоляция, контроль доступа и защищённое соединение.
- Нет защиты от cache stampede: одновременные miss могут все обратиться к базе.
  Недоступность Redis может резко увеличить нагрузку на PostgreSQL. Fail-open
  не означает гарантированную доступность под любой нагрузкой.
- Hit ratio, метрики Redis и сравнение под нагрузкой пока не добавлены.

## Тесты

```bash
pnpm cache:up
pnpm test:cache
```

Отдельный набор использует настоящий Redis на 6380, уникальный namespace
`test-task-cache:<uuid>` и случайную тестовую схему PostgreSQL. Удаляются только
собственные ключи, весь Redis не очищается. Тестовый TTL — 2 секунды, рабочий — 5.

Проверяются hit без SQL-транзакции списка, нормализация ключей, изоляция пользователей
и фильтров, пагинация, общий кэш двух приложений, TTL без продления на GET,
инвалидация после записи и защита от позднего SET, аутентификация даже при hit, повреждённые данные,
отсутствие утечки дополнительных полей и fallback. Unit-тесты отдельно проверяют
ошибки GET/SET и настройки ограниченного ожидания команд.

Обычные e2e-тесты отключают Redis, чтобы их схемы не пересекались через кэш.
`test:balancing` и нагрузочная лаборатория также явно отключают кэш: предыдущие
результаты относятся к SQL-пути. Для измерения кэша нужен отдельный сценарий
с прогревом и учётом hit/miss.

Основные файлы: `src/tasks/tasks-cache.service.ts`, `src/tasks/tasks.service.ts`,
`src/tasks/tasks.module.ts`, `test/task-cache.redis-spec.ts`. Для инвалидации добавлена
миграция `add_task_cache_generation`; сами кэшированные страницы остаются только в Redis.

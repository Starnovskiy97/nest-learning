# Урок 2. Ограничение запросов перед приложением

## Что добавлено

```text
HTTPie / браузер → localhost:8080 → Nginx в Docker
                                      ↓
                            host.docker.internal:3000
                                      ↓
                              NestJS на компьютере
```

Nginx ограничивает обращения к `/auth/login` по IP соединения. Допустимые
запросы передаются NestJS, избыточные получают JSON с HTTP 429 до вызова
контроллера, scrypt или базы. Остальные маршруты проксируются без этого лимита.
JWT по-прежнему проверяет NestJS: прокси не устанавливает личность пользователя.
Все методы на пути входа считаются, включая неуспешные и невалидные запросы.

## Запуск

```bash
pnpm db:up
pnpm start:dev
```

В другом терминале:

```bash
pnpm proxy:up
http GET :8080/
http POST :8080/auth/login email="anna@example.com" password="learning-password-123"
```

Используй данные уже зарегистрированного учебного пользователя. Порт приложения
должен быть 3000. Образ Nginx скачивается при первом запуске.
`host.docker.internal` ведёт из контейнера на компьютер, где запущен NestJS.
Для Docker на Linux добавлено соответствие `host-gateway`; приложение должно
быть доступно с Docker-сети, а не слушать исключительно loopback.

Nginx включён отдельным профилем Compose: `pnpm db:up` запускает только PostgreSQL.
Команда `pnpm proxy:up` не запускает и не перезапускает приложение или базу.
Порт прокси 8080 опубликован только на loopback компьютера.

```bash
pnpm proxy:logs
pnpm proxy:stop
```

Если NestJS не запущен, Nginx может работать, но на запрос ответит **502**.
Если upstream не отвечает вовремя — возможен **504**.
После правки шаблона перезапусти контейнер с повторной генерацией конфига:

```bash
docker compose --profile proxy up -d --force-recreate nginx
docker compose --profile proxy exec nginx nginx -t
```

## Как устроен лимит

Файл: `infra/nginx/default.conf.template`.

```nginx
limit_req_zone $binary_remote_addr zone=login_per_ip:10m rate=10r/m;

location ~* ^/auth/login/?$ {
    limit_req zone=login_per_ip burst=5 nodelay;
    proxy_pass http://${API_UPSTREAM};
}
```

- `$binary_remote_addr` — компактное представление IP соединения, ключ лимита.
- `zone=login_per_ip:10m` — 10 мегабайт общей памяти для состояния лимитера,
  **не десять минут**. Память общая между worker-процессами этого Nginx.
- `rate=10r/m` — средняя разрешённая скорость: 10 запросов в минуту.
- `burst=5` — запас для короткого всплеска сверх средней скорости.
- `nodelay` — допустимый всплеск передаётся сразу; лишние запросы отклоняются,
  а не ждут в очереди Nginx.
- `limit_req_status 429` — возвращать 429 вместо стандартного для этого модуля 503.

Это алгоритм leaky bucket, **не фиксированный счётчик «10 за календарную минуту»**.
На пустом состоянии быстрый всплеск обычно пропускает 6 запросов: первый и 5
дополнительных. Занятая ёмкость освобождается примерно по одному месту каждые
6 секунд. Запрос после 429 не обязательно должен ждать целую минуту.
Эти значения учебные, а не универсальная рекомендация для продакшена.

Совпадение пути нечувствительно к регистру, допускает завершающий слеш
и не зависит от query-параметров. Это важно: NestJS с Express по умолчанию
также допускает регистр и завершающий слеш. Варианты маршрута не должны
получать независимые лимиты или обходить ограничение.

`${API_UPSTREAM}` заменяется при старте официального Docker-образа Nginx.
Остальные `$...` — переменные самого Nginx; фильтр envsubst оставляет их нетронутыми.

## Проверка без воздействия на пользователей и базу

```bash
pnpm test:proxy
```

Тест запускает настоящий Nginx с тем же шаблоном, временный HTTP-сервер-заглушку
на случайном порту и удаляет свой контейнер после завершения. Запущенные
контейнеры приложения и PostgreSQL не трогает. Не читает `.env`, не проверяет
реальные пароли и не создаёт данные. Нужен работающий Docker; запускать локально
в доверенной сети, поскольку заглушка кратковременно слушает `0.0.0.0`.

Проверяется:

- Часть одновременных запросов допускается, избыток получает JSON 429 и `no-store`.
- Количество запросов, полученных заглушкой, совпадает с количеством допущенных:
  отклонённые запросы **не дошли до приложения**.
- Регистр пути, слеш, query и подставленный `X-Forwarded-For` не обходят лимит.
- Другой маршрут работает после исчерпания лимита входа.
- Authorization передаётся upstream, клиентский `X-Forwarded-For` перезаписывается.
- После паузы запросы снова допускаются.

В первом запуске из 20 запросов 6 дошли до заглушки, 14 получили 429.
Тест не использует scrypt, поэтому быстро заполняет лимит без нагрузки на CPU
от проверки паролей. Общее время включает паузу около 6,5 секунды.

Для ручной проверки через реальное приложение можно быстро повторить запрос
с невалидным DTO — он не запустит scrypt:

```bash
for i in {1..12}; do
  http --ignore-stdin --print=h POST :8080/auth/login email="not-an-email"
done
```

Сначала ожидаются 400 от NestJS, затем 429 от Nginx. При медленном выполнении
часть ёмкости успеет восстановиться. В логах для отклонений:
`status=429 upstream=- limit=REJECTED`. Access log не содержит Authorization,
тела запроса или query string. Не передавать пароли и токены в URL:
другие логи, в частности error log, могут содержать полный URI.

## Границы решения

- **IP не равен человеку:** общий адрес офиса делит один лимит. Это базовая
  защита потока, не полноценная защита аккаунта от распределённого перебора.
- Лимит действует только через **8080**. Прямой порт **3000** его обходит.
  В учебной среде он оставлен для разработки. В продакшене upstream нужно
  закрыть от внешних клиентов сетью/firewall и открыть только для прокси.
- Счётчики общие внутри одного Nginx, но не между независимыми экземплярами.
  Пересоздание контейнера теряет состояние. Redis в этом шаге не используется.
- Перед Nginx пока нет доверенного CDN/прокси. Используется IP соединения,
  а не клиентский заголовок. Если поставить CDN, без настройки доверенных
  адресов лимит может начать считать всех клиентов одним адресом CDN.
- `X-Forwarded-For` перезаписывается, а NestJS не настроен слепо доверять прокси.
  Сейчас внутри NestJS лимита по IP нет. В дальнейшем доверие настраивается
  отдельно и только для известной топологии, не простым «доверять всем».
- Лимит частоты не ограничивает сам по себе число одновременно выполняющихся
  дорогих операций. Нужны отдельные решения для параллелизма и общей нагрузки.
- Нет TLS, защиты регистрации и бизнес-лимитов по проверенному пользователю.
- Нет гарантии однократного создания задачи: это следующий урок об идемпотентности.

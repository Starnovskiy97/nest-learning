# Урок 5. Два экземпляра NestJS за Nginx

## Что запускаем

```text
                          ┌→ NestJS :3000 ─┐
Клиент → Nginx :8080 ──────┤               ├→ PostgreSQL :5433
                          └→ NestJS :3001 ─┘
```

Это два отдельных процесса одного приложения на компьютере, не два разных
микросервиса. Код, DATABASE_URL и JWT_SECRET одинаковые. Nginx работает в Docker.
Redis, sticky sessions, кэш и очереди пока не нужны.

## Запуск

Сначала поднять базу:

```bash
pnpm db:up
```

В первом терминале:

```bash
pnpm start:instance:1
```

Во втором:

```bash
pnpm start:instance:2
```

Если `pnpm start:dev` уже занимает порт 3000, он может быть первым экземпляром:
не запускай поверх него ещё один. Оба процесса читают один локальный `.env`.
Команды `start:instance:*` запускают TypeScript через ts-node без билда и без watch.
В tsconfig включён experimentalResolver ts-node, чтобы `.js`-импорты внутри
сгенерированного Prisma Client находили исходные `.ts`-файлы. Это не меняет
настройки разрешения модулей tsc. Возможен warning зависимости ts-node
о deprecated fs.Stats; он не означает ошибку запуска.

После запуска обоих процессов:

```bash
pnpm proxy:balanced:up
```

Команда накладывает `compose.balanced.yaml` на базовый Compose и пересоздаёт
только тот же сервис nginx при изменении его конфигурации. PostgreSQL и данные
не пересоздаются. Прежний порт 8080 сохраняется; новый контейнер прокси рядом
с прежним не создаётся. Настройка upstream читается при старте контейнера.

## Как увидеть распределение

```bash
for i in {1..8}; do
  http --ignore-stdin --print=h GET :8080/
done
```

В ответах есть учебный заголовок:

```http
X-Upstream-Addr: 192.168.65.254:3000
```

или адрес с портом 3001. Конкретный IP зависит от Docker: это адрес компьютера,
доступный из контейнера. Смотри прежде всего на порт. В публичном продакшене
этот диагностический заголовок лучше убрать, чтобы не раскрывать внутренние адреса.

В `pnpm proxy:logs` также виден адрес выбранного upstream и его статус.
Строгое чередование каждого ответа не является контрактом: влияют другие запросы,
состояние серверов и планирование. Пока оба сервера доступны и имеют одинаковый
вес, нагрузка распределяется примерно поровну **по запросам**, не по CPU или времени.

## Конфигурация

Шаблон `infra/nginx/default.conf.template` после подстановки окружения содержит:

```nginx
upstream api_backend {
    zone api_backend 64k;
    server host.docker.internal:3000;
    server host.docker.internal:3001;
}
```

Оба маршрута proxy_pass теперь ссылаются на `http://api_backend`.
В группе также включён `keepalive 16`: кеш простаивающих HTTP-соединений
на worker Nginx, не предел параллельности и не пул PostgreSQL.
Без явного выбора другого алгоритма Nginx использует round-robin.
`zone` делит состояние upstream между worker-процессами одного Nginx.
Это отдельная зона, не хранилище лимита входа.

В базовом Compose `API_EXTRA_SERVER` пуст: upstream содержит только порт 3000.
Overlay добавляет строку второго сервера. Envsubst заменяет только разрешённые
переменные API_UPSTREAM и API_EXTRA_SERVER, а переменные Nginx оставляет нетронутыми.

## Почему не нужно «приклеивать» пользователя к экземпляру

JWT подписан одним секретом, который известен обоим экземплярам. Любой из них
может проверить токен и получить пользователя из общей базы. Локальной серверной
сессии, которую знал бы только первый экземпляр, у нас нет.

Данные задач тоже общие:

- Авторизация проверяется запросами PostgreSQL, независимо от выбранного API.
- Идемпотентность защищена общим уникальным ключом, не локальной Map.
- Конкурентный PATCH защищён версией в UPDATE, а не блокировкой в одном процессе.
- Счётчик лимита входа находится в одном Nginx перед обоими приложениями:
  второй NestJS не удваивает этот лимит.

Независимые Nginx со своими зонами памяти уже имели бы независимые лимиты.

## Автоматическая проверка без пользовательских данных

```bash
pnpm test:balancing
```

Нужны локальная PostgreSQL и Docker. Тест создаёт случайную изолированную схему,
два настоящих NestJS-приложения на свободных портах и временный контейнер Nginx
с тем же шаблоном. Для JWT использует отдельный тестовый секрет. Приложения
в этом тесте живут в одном Node-процессе и используют общий тестовый Prisma Client;
ручные команды выше запускают независимые процессы с независимыми пулами.

Проверяются по настоящему HTTP через прокси:

1. Вход и работа одного токена на обоих upstream.
2. Распределение запросов между двумя upstream по заголовку ответа.
3. 12 параллельных POST с одним ключом — одна задача и одинаковые ответы.
4. 12 параллельных PATCH с одной версией — один 200 и одиннадцать 409.
5. Общий IP-лимит входа после добавления второго API.

После завершения свои приложения, контейнер и схема удаляются. Работающие
пользовательские процессы и данные в public не затрагиваются. Тестовые HTTP-порты
кратковременно слушают 0.0.0.0 ради доступа из Docker: запускай локально
в доверенной сети. Это проверка корректности, не нагрузочный тест производительности.

## Почему это ещё не отказоустойчивый продакшен

`proxy_next_upstream off` намеренно сохранён: Nginx не повторяет запрос на другом
сервере внутри одной попытки. Если выбранный процесс недоступен, возможен 502.
Установка второго экземпляра сама по себе не обещает бесшовную работу при отказах.
Выявление отказов, пассивное исключение, безопасные повторы и graceful shutdown
нужно разобрать отдельно. Особенно опасны автоматические повторы POST/PATCH,
когда неизвестно, успел ли первый сервер записать результат.

Оба API и прокси сейчас на одной машине: её отказ выключит всё. База остаётся
одна. Порты 3000/3001 всё ещё доступны напрямую в учебной среде и обходят Nginx;
публичный доступ к ним в продакшене нужно закрыть. TLS здесь пока не добавлен.

## Следующее узкое место — соединения с базой

У каждого отдельного процесса свой Prisma/pg pool. Например, два пула по 10
соединений могут дать до 20 соединений, десять таких процессов — до 100.
Это пример расчёта, не настройка max_connections нашего сервера.
Кроме API, соединения нужны миграциям, тестам и другим клиентам.

Два API могут увеличить пропускную способность, если ограничением был один
Node-процесс, но не ускоряют автоматически SQL и не удваивают возможности базы.
При перегруженной PostgreSQL добавление API может лишь увеличить очередь ожидания.
Дальше стоит измерять задержки и размеры пулов, а не бесконечно добавлять процессы.

Воспроизводимый эксперимент: [load-testing.md](load-testing.md).

## Возврат к одному экземпляру

```bash
pnpm proxy:up
```

Базовая конфигурация вернёт upstream только на 3000; Nginx пересоздастся,
его локальное состояние лимита сбросится. После этого второй процесс можно
остановить Ctrl+C. `pnpm proxy:stop` останавливает прокси в любом режиме,
не выключая PostgreSQL и процессы NestJS.

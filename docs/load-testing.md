# Урок 6. Измеряем один и два экземпляра API

## Запуск

Нужны локальные PostgreSQL, Docker и установленные зависимости pnpm.
Запускать NestJS вручную или включать режим прокси на 8080 не нужно:
эксперимент поднимает свои процессы и контейнер на свободных портах.

```bash
pnpm db:up

# Проверка сценария: 8 измерений, примерно минута
pnpm lab:load --quick

# Основной эксперимент: 24 измерения, несколько минут
pnpm lab:load
```

Во время измерений не запускай одновременно тесты, сборку или другой бенчмарк.
Результат ноутбука зависит от фоновых процессов, температуры и настроек Docker.
Локальный адрес может оказаться туннелем: убедись, что DATABASE_URL действительно
ведёт в учебную базу. Скрипт отклоняет не-локальный hostname, но не распознаёт туннели.

## Что происходит

1. Создаётся случайная тестовая схема с миграциями проекта, одним автором
   и 10 000 задачами. Данные приложения в public не изменяются.
2. Через ts-node запускаются **отдельные Node-процессы**, а не два приложения
   в одном event loop. Каждый получает свой Prisma/pg pool с максимумом 5 соединений.
3. Временный Nginx использует тот же шаблон, что и обычный прокси проекта.
4. Измеряются GET `/` и GET `/tasks?limit=10`, оба через Nginx.
5. Для каждого маршрута нагрузка повышается от 1 к 8 и 32 параллельным клиентам.
6. Сравниваются один и два API. Во втором раунде порядок обратный: сначала два,
   потом один. Каждый режим получает новые процессы и новый контейнер прокси.
7. По завершении, обычной ошибке или обработанному Ctrl+C свои процессы,
   контейнер и схема очищаются. SIGKILL, сбой машины или принудительное завершение
   самого родительского процесса не дают гарантии очистки.

`--quick`: один раунд, параллельность 1/8, по 2 секунды измерения.
Обычный режим: два раунда AB/BA, параллельность 1/8/32, по 4 секунды.
Перед каждой ячейкой есть секунда прогрева без включения в статистику.
Это короткий учебный опыт, не длительный тест стабильности.

JWT выдаётся только внутри эксперимента отдельным тестовым секретом. Пароли
не проверяются под нагрузкой, rate limiting входа не участвует. `/tasks` выполняет
реальный Guard, чтение пользователя, выборку задач и count в транзакции.
Проверяются не только статусы 200, но и тело ответа: 10 элементов и total=10000.
Скрипт останавливает повышение нагрузки при ошибках измеряемых запросов.

Рабочие экземпляры на 3000/3001 и Nginx на 8080 не останавливаются и не меняются.
Ресурсы машины и сервера PostgreSQL всё равно общие! Два ts-node-процесса могут
потреблять около гигабайта RAM или больше; это не требование production-сборки.
Тестовые порты API слушают 0.0.0.0 ради доступа из Docker: запускать в доверенной
локальной сети. Лабораторный endpoint метрик защищён случайным заголовком
и существует только в `scripts/load-worker.ts`, не в обычном приложении.

## Как создаётся нагрузка

Используется **closed-loop** модель: каждый из C виртуальных клиентов посылает
следующий запрос только после полного ответа или ошибки предыдущего.
Соединения HTTP переиспользуются, HTTP pipelining не используется.

```text
Клиент 1: запрос → ответ → запрос → ответ
Клиент 2: запрос ───→ ответ → запрос
```

Параллельность одинакова при сравнении одного и двух API. Это не фиксированный
входящий RPS: когда ответы замедляются, генератор сам отправляет меньше запросов.
Поэтому этот опыт не моделирует независимый поток, который продолжает прибывать
при перегрузке. Для такого сценария нужен open-loop генератор и учёт пропущенных
запланированных запросов. Не переносить полученную p95 на произвольную нагрузку.

Каждый запрос имеет таймаут неактивности сокета 5 секунд. После окончания окна
новые запросы не запускаются, уже начатые завершаются. Фактическое elapsed включает
их завершение; измерение не обрывает их на искусственной границе.

## Что означают поля JSON-строки результата

| Поле | Значение |
| --- | --- |
| round / instances / path / concurrency | Раунд, число API, маршрут, число клиентов |
| successful / errors | Полностью проверенные успешные ответы и ошибки |
| rps | Успешные ответы / фактическое время измерения |
| p50Ms / p95Ms / p99Ms | Перцентили задержек **успешных** запросов, включая чтение и проверку тела |
| apiCpuPercent | Сумма user+system CPU дочерних API: 100% = одно полностью занятое ядро |
| apiRssMiB | Наибольшая наблюдённая сумма RSS процессов API |
| dbConnections | Наибольшее наблюдённое число соединений именно этих процессов |
| dbActive | Наибольшее наблюдённое число их соединений в состоянии active |
| generatorCpuPercent | CPU родителя, который генерирует нагрузку и собирает метрики |
| upstreams | Сколько разных upstream реально обработали успешные запросы |
| errorDetails | Группировка ошибок, включая неуспешные HTTP-статусы |

Перцентили рассчитываются nearest-rank по сохранённым задержкам, не по среднему.
Например, p95=9 мс означает, что не менее 95% измеренных успешных запросов
уложились в 9 мс. Если часть запросов упала, эту цифру нельзя рассматривать
в отрыве от errors: таймауты не попадают в успешную p95.

CPU берётся из process.cpuUsage каждого процесса. RSS и соединения с базой
опрашиваются примерно раз в 300 мс, поэтому краткие пики могут быть пропущены.
RSS включает память V8, ts-node и другие отображённые страницы, не только heap.
Сумма RSS может повторно учитывать разделяемые страницы и не равна точному
дополнительному расходу физической памяти всей машины.

Соединения определяются через pg_stat_activity по уникальному application_name.
Административные соединения и соединение самого мониторинга не включены.
active не означает «выполняет вычисления на CPU»: запрос может ждать блокировку
или I/O. Размер очереди ожидания внутри pg pool этим способом не измеряется.

**CPU/RAM PostgreSQL, Nginx и Docker VM автоматически здесь не измеряются.**
Для дополнительного наблюдения можно отдельно использовать:

```bash
docker stats --no-stream
```

Это моментальный срез, не полноценная временная серия. Генератор также работает
на этой машине и может стать ограничением. Низкий CPU API не доказывает, что
можно увеличить нагрузку бесконечно: ограничением могут быть прокси, сеть и база.

## Первый успешный короткий прогон

Пример одного запуска после включения upstream keep-alive, C=8:

| Маршрут | API | Успешных/с | p95 | API CPU | Соединения БД, наблюдённый максимум |
| --- | ---: | ---: | ---: | ---: | ---: |
| `/` | 1 | 8145 | 1,41 мс | 69% | 0 |
| `/` | 2 | 7859 | 1,51 мс | 81% | 0 |
| `/tasks?limit=10` | 1 | 1078 | 8,91 мс | 91% | 5 |
| `/tasks?limit=10` | 2 | 1274 | 7,74 мс | 147% | 10 |

Ошибок в этих измерениях не было. На одном клиенте второй процесс не дал
выигрыша. При C=8 список задач в этом запуске стал примерно на 18% быстрее,
но простой маршрут — нет. **Один двухсекундный прогон не доказывает устойчивый
выигрыш или проигрыш.** Сначала сравни раунды основного эксперимента и повтори его.

Обрати внимание: два API увеличивают не только доступный параллелизм JavaScript,
но и суммарный бюджет соединений с 5 до 10. Это не эксперимент, изолирующий
только влияние числа процессов. Для этого нужен отдельный контроль с одинаковым
общим бюджетом соединений. Уверенно приписывать весь выигрыш CPU нельзя.

## Основной прогон: два раунда AB/BA

28 октября 2026 года основной сценарий выполнил все 24 измерения без ошибок.
Ниже диапазоны наблюдений двух раундов, **не усреднённые перцентили**:

| Маршрут | C | API | Успешных/с | p95, мс | Максимум соединений БД |
| --- | ---: | ---: | ---: | ---: | ---: |
| `/` | 32 | 1 | 13 516–13 946 | 3,59–3,69 | 0 |
| `/` | 32 | 2 | 14 386–14 752 | 3,43–3,62 | 0 |
| `/tasks?limit=10` | 8 | 1 | 1058–1075 | 8,99–9,11 | 5 |
| `/tasks?limit=10` | 8 | 2 | 1189–1294 | 7,68–9,00 | 10 |
| `/tasks?limit=10` | 32 | 1 | 1103–1109 | 32,82–33,48 | 5 |
| `/tasks?limit=10` | 32 | 2 | 1599–1640 | 26,21–32,58 | 10 |

На одном API повышение C с 8 до 32 почти не увеличило RPS списка задач,
но p95 выросла примерно с 9 до 33 мс. Это хороший пример накопления ожидания,
а не полезного четырёхкратного роста пропускной способности.
Два API на C=32 увеличили RPS задач примерно на 44–49% в соответствующих раундах,
**не в два раза**. Для простого `/` улучшение при C=32 было около 6%,
а при C=1 второй API не дал выигрыша ни на одном маршруте.

Для задач при C=32 сумма CPU API составила около 80–85% у одного процесса
и 149–161% у двух. Прокси, Docker, база и генератор потребляют CPU дополнительно.
По этим данным нельзя установить единственную причину ограничения: в частности,
не измерены ожидание пула и CPU PostgreSQL. Следующий контрольный эксперимент —
одинаковый суммарный бюджет соединений при разном числе API.

## Неожиданное ограничение: короткие TCP-соединения

Первый вариант конфигурации не кешировал upstream-соединения. На частых запросах
возникли 502, а затем EADDRNOTAVAIL в локальном мониторинге: исчерпались доступные
локальные порты. Это не было доказательством предела производительности NestJS.

В upstream теперь включено `keepalive 16`: Nginx кеширует до 16 **неактивных**
соединений на worker, а существующие HTTP/1.1 и `Connection ""` позволяют
переиспользовать их. Это не лимит общего числа активных запросов и не pg pool.
После изменения короткий сценарий прошёл без ошибок. Настройка применяется
к новым контейнерам; уже работающий прокси сам не перечитывает шаблон.

## Что заключать из измерений

- RPS вырос при приемлемой p95 и без ошибок — есть польза в этом сценарии.
- RPS почти прежний, память и соединения выросли — второй API может быть лишним.
- RPS перестал расти, а p95 растёт — нужна диагностика узкого места.
- Появились 502/таймауты — сначала выяснить источник, не считать ошибки
  дополнительной «пропускной способностью».
- Проверяй разброс между AB и BA, не выбирай только самый красивый результат.

Это измерение development-запуска через ts-node, общей локальной базы и Docker
Desktop. Нет production-сборки, отдельного генератора, долгого steady state,
смешанного трафика и записей в базу. Полученные числа не являются SLO или
оценкой вместимости продакшена. Цель — научиться задавать вопросы измерениям.

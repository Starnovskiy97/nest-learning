# Учебная база данных

## Текущее состояние

PostgreSQL запущена через Docker Compose. Первая миграция создала таблицы
`User` и `Task`. `UsersService` и `TasksService` читают и сохраняют данные через
Prisma: пользователи, задачи и назначенные исполнители переживают перезапуск
приложения. Ранее созданные в памяти данные автоматически в базу не переносятся.

Цепочка зависимостей: `UsersModule` импортирует `PrismaModule`, который
предоставляет и экспортирует `PrismaService`. Сервис открывает соединение
при инициализации Nest и закрывает его при завершении приложения.
`TasksModule` импортирует и `PrismaModule` для хранения задач, и `UsersModule`
для проверки пользователя перед назначением.

У задачи без исполнителя API возвращает `assigneeId: null`. Это соответствует
`NULL` в базе, а не отсутствующему полю JSON. Входной DTO по-прежнему допускает
только положительный целочисленный `assigneeId`: снятие исполнителя через `null`
пока не реализовано.

Изменение полученного JS-объекта само по себе не меняет строку в базе.
Для сохранения нужен явный `prisma.task.update()`. Отсутствующие в PATCH поля
передаются как `undefined`, и Prisma 7 с текущими настройками оставляет их
без изменений. Значение `false`, наоборот, сохраняется.

Ошибка Prisma `P2025` при обновлении или удалении преобразуется в HTTP 404.
Ошибка внешнего ключа `P2003` при назначении также преобразуется в 404 для
несуществующего пользователя. Неожиданные ошибки не маскируются под 404.

## Основные файлы

- `compose.yaml` — контейнер PostgreSQL 17 и постоянный том данных.
- `.env.example` — пример локального адреса подключения.
- `.env` — настройки подключения; файл не предназначен для Git.
- `prisma.config.ts` — конфигурация Prisma CLI и чтение `DATABASE_URL`.
- `prisma/schema.prisma` — модели данных и связь между ними.
- `prisma/migrations/` — SQL-миграции, которые нужно сохранять в Git.
- `src/generated/prisma/` — сгенерированный клиент; вручную не редактируется.

Логин и пароль в Compose предназначены только для локального обучения.
Порт `5433` доступен только на этой машине; внутри контейнера используется `5432`.

## Команды

При первоначальной настройке скопировать `.env.example` в `.env`.

```bash
pnpm db:up
pnpm db:migrate
pnpm db:generate
pnpm db:status
```

После изменения схемы создаётся новая миграция с осмысленным названием:

```bash
pnpm db:migrate --name describe_change
pnpm db:generate
```

Просмотр таблиц в браузере:

```bash
pnpm db:studio
```

Остановка контейнера без удаления данных:

```bash
pnpm db:down
```

Данные сохраняются в томе `postgres_data`. Не использовать `docker compose down -v`,
если данные нужны: флаг `-v` удаляет том.

## Как устроена связь

Миграция `add_user_credentials` добавляет `User.email` с уникальным индексом
и `User.passwordHash`. Обе колонки nullable для сохранения существующих
пользователей. Подробности регистрации: [auth.md](auth.md).

Один пользователь может быть исполнителем нескольких задач. У задачи может
не быть исполнителя: `assigneeId` допускает `NULL`.

- `@id` — первичный ключ, уникально идентифицирующий запись.
- `@default(autoincrement())` — база выдаёт следующий идентификатор.
- `@default(false)` — начальное значение статуса задачи.
- `assigneeId` — реальная колонка и внешний ключ на `User.id`.
- `assignee` и `tasks` — поля связи Prisma, а не дополнительные колонки.
- `onDelete: Restrict` — база не даст удалить пользователя с назначенными задачами.
- `@@index([assigneeId])` — индекс для поиска задач по исполнителю.

Внешний ключ не позволит записать несуществующий `assigneeId`, даже если
приложение забудет проверить пользователя.

Миграция — сохранённое изменение структуры базы. Prisma сравнивает схему
с историей миграций, генерирует SQL и применяет его к локальной базе.
Применённые миграции не переписывают: изменения оформляют следующей миграцией.

## Асинхронная работа

Запросы Prisma возвращают Promise: результат придёт после ответа базы.
`await` позволяет дождаться результата перед проверкой пользователя или
изменением задачи. Nest умеет дожидаться Promise, возвращённого контроллером.

## Фильтрация задач

```bash
http GET :3000/tasks completed==false
http GET :3000/tasks assigneeId==1
http GET :3000/tasks completed==false assigneeId==1
```

`==` в HTTPie задаёт query-параметр. `@Query()` передаёт параметры в
`FilterTasksDto`. `ValidationPipe` с `transform: true` возвращает контроллеру
DTO с явно преобразованными и проверенными значениями.

- `completed` принимает только строки `true` и `false`, преобразуемые в boolean.
- `assigneeId` — положительное целое число в диапазоне PostgreSQL `Int`.
- Неизвестные параметры, повторяющиеся значения и неверные форматы дают 400.
- Без параметров возвращается первая страница задач; два фильтра соединяются условием AND.
- Несуществующий исполнитель в фильтре даёт пустой список, а не 404.

Преобразование boolean выполняется явно: `Boolean('false')` вернул бы `true`,
поскольку любая непустая строка считается истинной. Фильтрация происходит
в PostgreSQL через `where` Prisma, а не в массиве после загрузки всех задач.

## Пагинация задач

```bash
http GET :3000/tasks page==1 limit==10
http GET :3000/tasks page==2 limit==5 completed==false assigneeId==1
```

Ответ `GET /tasks` теперь содержит объект, а не массив:

```json
{
  "items": [],
  "total": 0,
  "page": 1,
  "limit": 10,
  "totalPages": 0
}
```

- `page` — номер страницы, начиная с 1; по умолчанию 1.
- `limit` — размер страницы от 1 до 100; по умолчанию 10.
- `items` — задачи текущей страницы, упорядоченные по `id` по возрастанию.
- `total` — общее количество задач, соответствующих фильтрам, до пагинации.
- `totalPages` — `Math.ceil(total / limit)`; для пустого списка 0.

Страница за пределами списка возвращает пустой `items` и прежний `total`,
а не 404. Неверные параметры пагинации возвращают 400. Слишком большое
смещение, выходящее за диапазон Prisma `skip`, тоже отклоняется с 400.

Prisma получает `skip: (page - 1) * limit` и `take: limit`. Пример:
страница 3 по 10 элементов пропускает первые 20 и запрашивает следующие 10.

Выборка и подсчёт используют один и тот же `where`. Они выполняются
в транзакции с уровнем `RepeatableRead`, чтобы список и количество
соответствовали одному снимку данных при параллельных изменениях.
Схема базы не менялась, новая миграция не требуется.

## Тесты

Для e2e-тестов PostgreSQL должна быть запущена:

```bash
pnpm db:up
pnpm test:e2e --runInBand
```

Каждый набор тестов создаёт отдельную схему `test_<случайный идентификатор>`,
применяет к ней SQL-миграции и удаляет её после завершения. Очистка выполняется
только внутри этой схемы: данные приложения в `public` не затрагиваются.

Флаг Node.js `--experimental-vm-modules` в команде e2e нужен Jest для
динамических импортов сгенерированного Prisma Client. Он может выводить
предупреждение об экспериментальной возможности Node.js.

# Урок 4. Оптимистическая блокировка задач

## Проблема

Две вкладки или два устройства прочитали одну задачу. Первый клиент сохранил
изменения. Второй ещё не знает о них и может затереть их старой формой.
HTTP-запросы не выполняются целиком в общей очереди: пока один ждёт базу,
другой тоже может читать и писать. BroadcastChannel улучшает синхронизацию
вкладок, но не заменяет проверку в базе и не связывает разные устройства.

## Новый контракт

Ответы задач содержат `version`. Новые и существующие на момент миграции задачи
начинают с 1. Теперь **каждый PATCH требует version в теле** — это изменение
контракта, старым клиентам нужно добавить её из полученного ответа.

```bash
http GET :8080/tasks/1 "Authorization:Bearer <JWT>"

# Если GET вернул version=1:
http PATCH :8080/tasks/1 "Authorization:Bearer <JWT>" \
  title="Новое название" version:=1
```

Успех — 200, ответ содержит `version: 2`. Если другая вкладка повторит PATCH
с `version: 1`, получит 409 Conflict, и её изменения не сохранятся.
ID и версию нужно брать из фактического ответа; порт 3000 тоже поддерживается.
Для 8080 должны работать NestJS и Nginx.

- Версия обязательна, целое число от 1 до 2147483646 включительно.
- Нет версии, null, строка `"1"`, дробь или значение вне диапазона — 400.
- Версия не совпадает с текущей — 409, даже если она больше текущей.
- Чужая или отсутствующая задача при корректном DTO — прежний 404, не 409.
- Каждый успешный PATCH увеличивает версию на 1, даже с теми же значениями
  полей или только с `version`. Пустое тело `{}` теперь даёт 400.
- Ошибки валидации, отсутствие исполнителя и конфликты не изменяют задачу
  и не увеличивают версию.
- POST не принимает version: начальным значением управляет сервер.
- DELETE пока не требует версии и может удалить задачу независимо от её версии.

Верхний предел предотвращает переполнение PostgreSQL INTEGER при увеличении.
При достижении 2147483647 дальнейшие PATCH недоступны в этой учебной модели.

## Почему это защищает от гонки

Упрощённый SQL операции обновления:

```sql
UPDATE "Task"
SET title = 'Новое название', version = version + 1
WHERE id = 1 AND "ownerId" = 7 AND version = 1
RETURNING *;
```

Условие версии и изменение находятся в **одной операции**, а не в независимых
«прочитать → сравнить → записать». Если конкурент успел обновить задачу, условие
версии больше не выполнится. PostgreSQL при стандартном Read Committed
согласует конкурентные изменения строки, в том числе ожидание другой транзакции
и проверку условия на обновлённой строке.

В Prisma это `where: { id, ownerId, version }` и
`data: { ..., version: { increment: 1 } }`.

Предварительный `findOne` нужен для понятного 404, раннего конфликта и проверки
исполнителя, но **не является блокировкой**. Поэтому условие повторяется в самом
UPDATE. При отсутствии совпавшей строки Prisma возвращает P2025. Сервис проверяет,
доступна ли задача автору: если нет — 404, иначе — 409. Эта проверка отражает
наблюдаемое состояние на момент чтения; не обещает, что оно больше не изменится.

Отдельная транзакция для такой одиночной записи не нужна: UPDATE уже атомарен.
Оптимистическая блокировка не означает, что PostgreSQL вообще не использует
блокировки: мы просто не держим блокировку на время редактирования формы.

## Поведение фронтенда

1. Сохранять версию вместе с прочитанной задачей.
2. Отправлять именно эту версию вместе с правкой.
3. После успеха использовать задачу и новую версию из ответа.
4. При 409 показать конфликт, получить свежую задачу и предложить пользователю
   сравнить или повторно применить изменения.

Нельзя просто получить свежую версию и автоматически отправить старую полную
форму с ней: это обойдёт смысл защиты и снова затрёт чужие изменения.
Сливать независимые изменения автоматически можно лишь с явно выбранными правилами.

## Отличие от идемпотентности

- Idempotency-Key на POST защищает от повторного создания при повторной доставке.
- Version на PATCH защищает от применения правки к устаревшему состоянию.

Повтор PATCH после потерянного успешного ответа получит 409 со старой версией.
Из одного 409 клиент не может понять, прошёл ли его предыдущий запрос или выиграл
другой: нужно получить актуальное состояние. Идемпотентность PATCH здесь не реализована.

Снимок идемпотентного POST теперь также возвращает `version: 1`, включая старые
сохранённые ключи. Это версия первоначального создания в текущем формате ответа,
не текущая версия задачи. Для редактирования после повтора POST нужно прочитать
задачу заново. Сами сохранённые ключи и задачи не удаляются.

## Проверки

```bash
pnpm test:e2e --runInBand task-concurrency
```

Проверяются устаревшая и актуальная версии, валидация, сохранность полей при отказе,
авторизация и 12 параллельных PATCH через два приложения с общим тестовым клиентом
базы: один 200, остальные 409. Отдельные тесты воспроизводят обновление и удаление
между предварительным чтением и UPDATE, чтобы проверить именно защиту в базе.

Миграция `add_task_version` добавляет NOT NULL-колонку с DEFAULT 1 без удаления
данных. Все записи через этот API увеличивают версию на PATCH; прямые SQL-записи
и другие сервисы также должны соблюдать эту договорённость, иначе защиту можно
обойти. Нельзя считать версию номером изменения, сделанного любым возможным писателем.
